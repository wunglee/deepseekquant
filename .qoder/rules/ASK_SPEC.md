# ask 生成规范（独立说明）

目的
- 为评审 ask 提供统一的写作模板与逐节说明，保证专家可读性、机器可校验性、术语一致性。
- 与脚本校验一致，避免重复、歧义和无效信息。

写作总原则
- 全文中文；术语统一使用“本轮改进”，不混用“上一轮修改”。
- 主要章节使用二级标题（##）；代码评审内部的子章节使用三级标题（###）。
- 禁止出现内部项目管理类文档引用（如 SPRINT.md、TODO.md）；禁止包含“测试计划（验收后执行）”。
- 固定结尾语句必须存在：“重要：请尽可能详尽和充分，不要遗漏和简化，谢谢！”。
- 定位与边界：ask 面向业务领域专家；禁止包含技术实现/架构/性能/测试/项目管理问题，这些由技术团队自行解决与交付；仅围绕业务口径、规则、数据源、阈值、合规路径、审计要求与策略意图提问。
- 语言与称谓：全文中文；称谓统一使用“您”，在关键问题处可多次使用“请您确认”以保持礼貌与清晰（通常分布于“本轮业务问题”等部分）。

模板结构与逐节说明
## 📋 Phase边界声明（必须）
- 作用：界定当前评审范围与阶段边界，避免跨域或越级讨论。
- 内容：
  - 当前阶段说明（例：仅做风险模块协调器与前置检查，不讨论生产发布）。
  - 系统范围（例：仅 core_bak_refactored 临时系统）。
  - 本轮状态（例：不改动代码；现有单测通过 15/15）。
- 禁忌：不要引入未来迭代或跨系统部署的内容。

## 背景说明
- 作用：给出本轮评审的目的与上下文，一段话即可。
- 内容：本轮评审目标（例：完成专家业务口径确认）、代码变更状态、测试状态。
- 子项：
  - #### 📚 依赖上下文与设计文档清单（必须）
    - 列出与本轮评审直接相关的设计文档、配置文件与基础设施路径。
    - 禁忌：不要在此处展开代码级细节（代码细节在“代码评审”中）。

## 🧩 代码评审
- 作用：本轮评审的核心内容，统一承载“承接上一轮答复 → 验收条目 → 改进清单 → 架构变更（如有）”。
- 子节顺序（固定）：
  1) ### 上一轮答复摘要与本轮改进（必须)
     - 摘要回顾：提炼上一轮 answer 的关键点；禁止复制原文。
     - 代码清单汇总：列出本轮涉及的核心实现、测试与配置依赖；需与实际修改文件一致。
     - 本轮改进映射：逐条映射本轮已实施/拟实施的改进到上一轮答复的具体条目与改进考虑（配置驱动/无默认值/不改变既有行为）。
  2) ### 业务视角的代码实现评审要点
     - 从业务契约角度说明方法/字段/返回/异常与业务口径的一致性、触发可靠性、数据质量治理、市场差异化与合规路径等。
  3) ### ✅ 本轮改进验收清单（专家确认）
     - 作用：用于验证“本轮改进”的具体条目。示例：规则 Schema、评分公式、阻断阈值、动作映射、审计字段、exec 集成点等。
     - 要求：与“本轮改进（清单与关键评审）”强相关，便于专家逐条勾选确认。
  4) ### 本轮改进（清单与关键评审）（必须)
     - 列出代码文件与关键方法；对方法的输入/输出/异常与业务口径做详细解释；给出测试覆盖的关键评审点。
     - 术语：统一使用“本轮改进”；禁止“上一轮修改”。
  5) ### 🧩 架构变更与影响（如果有）
     - 仅在存在架构层面的变化时填写；否则可保留空节或简述“本轮无架构变更”。

## 本轮业务问题（下一轮需解决，非本轮验收内容）
- 作用：提出下一轮需要专家提供思路的方向，避免我们主导“实施纲要”。
- 边界：仅围绕业务主题；不得包含技术实现、架构、性能、测试或项目管理事项。
- 建议拆分为三类子项：
  - ### 领域知识：需专家界定的业务口径与定义（例：数据质量维度定义与来源、分级口径）。
  - ### 优化机会：可能的业务价值提升点（例：降低误触发率、提升合规一致性、按市场策略校准阈值、优化运营与审计成本）。
  - ### 实施路径：可选的落地路线与依赖（例：exec 域集成点与审计字段最小集），请您确认具体方案前置条件。

## 🔗 相关文件（参考）
- 作用：给出便于定位的参考路径（实现与测试）。
- 内容：核心实现文件、测试文件等（示例：core_bak_refactored/core/risk/risk_calculator.py；tests/.../risk_calculator_test.py）。

校验与自动化
- 机器锚点：各章节标题文本需与模板一致；允许标题层级有差异（校验忽略 # 数量）。
- 相邻性规则：在“代码评审”块中，“验收清单”需与“本轮改进（清单与关键评审）”保持强相关（模板顺序固定，脚本已校验标题存在）。
- 禁止项：出现 SPRINT.md、TODO.md、测试计划（验收后执行）会触发失败。
- 运行方式：python scripts/validate_ask.py --path docs/ask.md。

生成与重建（强制）
- 每轮 ask.md 必须重新生成，不得在旧 ask.md 上修改或保留历史内容。
- 正确流程：先删除旧 ask.md（delete_file），再创建新 ask.md（create_file）。
- 生成后验证：检查 line changes 仅显示 +N added（纯新增），不应出现 -M removed（说明是修改）。
- 内容独立性：本轮 ask.md 只包含本轮咨询相关内容；上一轮内容仅能在“上一轮答复摘要与本轮改进”中做摘要，不得复制原文。

术语与一致性
- 统一用语“本轮改进”；避免“上一轮修改”。
- “验收清单”特指针对“本轮改进”的验证条目。
- “代码清单汇总”需与实际变更一致，保证可追溯性。
