# DeepSeekQuant 项目工作流程规范

> **版本**: v1.0  
> **最后更新**: 2024-11-12  
> **适用范围**: 所有开发、评审、提交流程

---

## 📋 核心原则

1. **阶段验收制**: 每个阶段必须经专家验收评审通过后才能提交代码
2. **小步迭代**: "小步修改 → 跑测 → 继续"的开发节奏
3. **文档同步**: 代码与文档同步更新，通过Git统一管理
4. **TODO驱动**: 专家改进建议必须记录到TODO，形成改进闭环

---

## 🔄 完整工作流程

### 阶段1：需求分析与规划

**输入**:
- 用户需求描述
- 现有代码状态

**输出**:
- 任务分解计划
- 文件范围确定

**规范**:
- ✅ 明确限定工作范围（只处理指定文件）
- ✅ 主动排除无关文件干扰
- ✅ 记忆要求：严格控制任务边界

---

### 阶段2：代码实施

**流程**:
```
1. 理解架构设计 → 2. 小步修改 → 3. 运行测试 → 4. 测试通过 → 5. 继续下一步
```

**规范**:
- ✅ 先理解架构设计文档要求
- ✅ 结合改进建议进行实施
- ✅ 每次修改后必须运行测试
- ✅ 确保所有测试通过才继续
- ❌ 禁止未经测试的大规模修改

**代码规范**:
- ✅ 新增功能添加TODO注释：`# TODO: 补充了XXXX，待确认，来源：XX文件`
- ✅ 遵循现有代码风格和架构分层

---

### 阶段3：专家评审准备

#### 3.1 更新TODO文档

**时机**: 代码实施完成后、生成ask.md之前

**位置**: `core_bak_refactored/<模块>/TODO.md`

**内容**:
- ✅ 记录本阶段完成的功能
- ✅ 标记已完成项 `[x]`
- ✅ 添加测试通过记录
- ⚠️ **预留专家建议区域**（评审后填写）

**示例**:
```markdown
### 已完成
- [x] **阶段3：国际化补充检查** - RiskCalculator集成MarketConfigManager，专家评审87/100，批准发布

### 待办事项（专家改进建议）

#### ⚠️ P1: XX功能改进（专家建议 - 阶段X评审）
**问题说明**: ...
**修复方案**: ...
**待办**:
- [ ] 具体任务1
- [ ] 具体任务2
```

---

#### 3.2 生成评审文档 ask.md

**位置**: `docs/ask.md`（临时文件，不纳入历史版本）

**规范**:
- ✅ **称谓统一**: 面向外部专家时，禁止使用"专家"，统一使用"您"
- ✅ 包含完整的问题背景和代码片段
- ✅ 附录包含相关文件清单
- ✅ 明确评审请求（评估哪些方面）

**结构**:
```markdown
# 第X轮咨询 - 阶段X: XXX评审

## 背景说明
## 当前状态快照
## 核心问题
## 评审请求
## 附录：相关文件清单
```

**⚠️ 重要**: 生成后等待用户确认，**不要**立即追加到consultation.md

---

### 阶段4：专家评审

#### 4.1 提交评审

**用户操作**:
- 确认ask.md内容
- 提交给专家评审
- 专家回复保存到 `docs/answer.md`

---

#### 4.2 提取专家回复

**AI操作**:
0. 检查是否有遗漏（核对 `docs/ask.md` 的所有问题是否均被回答；如有遗漏，生成补充问题清单并回传）
1. 读取 `docs/answer.md`
2. 提取关键评审结论
3. 提取改进建议（按优先级分类）

**输出**:
- 遗漏项清单（如有）
- 评审总结（通过/不通过/有条件通过）
- 高优先级问题清单
- 中低优先级建议清单

---

#### 4.3 ⭐ 记录专家建议到TODO（新增规范）

**时机**: 提取专家回复后立即执行

**操作**:
```bash
# 1. 更新TODO.md
vim core_bak_refactored/<模块>/TODO.md

# 2. 添加专家建议
### 待办事项（专家改进建议）

#### ⚠️ P1: XX（专家建议 - 阶段X评审）
- [ ] 任务1
- [ ] 任务2

#### 💡 P2: XX（专家建议 - 阶段X评审）
- [ ] 任务1

# 3. 提交
git add core_bak_refactored/<模块>/TODO.md
git commit -m "docs: 记录阶段X专家改进建议到TODO"
```

**规范**:
- ✅ 按优先级分类（P0/P1/P2/P3）
- ✅ 标注来源（专家建议 - 阶段X评审）
- ✅ 包含问题说明和修复方案
- ✅ 列出具体待办任务清单

---

#### 4.4 修复高优先级问题

**流程**:
```
1. 修复P0/P1问题 → 2. 运行测试 → 3. 测试通过 → 4. 提交修复
```

**规范**:
- ✅ 优先修复P0、P1级别问题
- ✅ 每次修复后运行测试
- ✅ 独立提交每个修复
- ⚠️ P2/P3问题记录到TODO，下阶段处理

---

### 阶段5：代码提交

#### 5.1 提交检查清单

**必须全部满足**:
- [ ] 所有测试通过
- [ ] TODO已更新（包含本阶段完成项）
- [ ] TODO已记录专家建议（如有评审）
- [ ] ask.md已生成并确认
- [ ] 专家评审已通过（如需要）
- [ ] consultation.md准备清空

---

#### 5.2 Git提交规范

**提交顺序**:
```bash
# 1. 提交功能代码
git add <功能相关文件>
git commit -m "feat/fix: 简短描述

详细说明:
- 修改点1
- 修改点2

Tests: X/X passed ✅"

# 2. 提交TODO更新（如包含专家建议）
git add core_bak_refactored/<模块>/TODO.md
git commit -m "docs: 记录阶段X专家改进建议到TODO"

# 3. 清空consultation.md（阶段完成后）
echo "# 专家咨询记录" > docs/consultation.md
git add docs/consultation.md
git commit -m "chore(docs): 清空consultation.md，阶段X已完成"
```

**Commit Message格式**:
```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type类型**:
- `feat`: 新功能
- `fix`: 修复bug
- `docs`: 文档更新
- `refactor`: 重构
- `test`: 测试相关
- `chore`: 构建/工具相关

---

### 阶段6：文档管理

#### 6.1 文档目录结构

**`docs/` 目录**:
```
docs/
├── ask.md              # 临时：当前向专家提问（不提交历史）
├── answer.md           # 临时：当前专家回答（不提交历史）
├── consultation.md     # 版本控制：本次完整对话记录（多轮追加）
├── WORKFLOW.md         # 版本控制：工作流程规范（本文档）
├── PLAN.md             # 版本控制：项目计划
├── PROGRESS.md         # 版本控制：项目进展
├── ARCHITECTURE.md     # 版本控制：架构文档
├── IMPROVEMENTS.md     # 版本控制：改进建议
└── CHANGELOG.md        # 版本控制：变更日志索引
```

---

#### 6.2 consultation.md管理规范

**咨询阶段**:
1. AI生成ask.md → **等待用户确认**
2. 用户确认后 → 立即追加到consultation.md
3. 用户提供answer.md → AI读取并立即追加到consultation.md
4. 重复1-3直到开始实施

**实施阶段**:
4. 实施代码功能
5. 更新TODO.md（包含专家建议）
6. 提交代码 + consultation.md

**提交后**:
7. **清空consultation.md** → 只保留标题 `# 专家咨询记录`
8. 开始新一轮

**⚠️ 重要规则**:
- ❌ **不要**在用户确认前追加ask.md到consultation.md
- ✅ **必须**在每个阶段提交后清空consultation.md
- ✅ consultation.md通过Git历史管理版本演进

## 🔍 特殊场景处理

### 场景1：国际化补充检查（独立阶段）

**规范**:
- 作为独立补充阶段执行（如阶段2.5、阶段3）
- 不打断原有开发流程
- 检查范围：市场类型一致性、国际增强模块集成、区域化默认值、日志国际化、时间货币单位
- 发现问题后直接修复并提交，通过consultation.md记录

**流程**:
```
发现国际化问题 → 直接修复代码 → 运行测试 → 提交代码 → 
记录到consultation.md → 生成ask.md → 提交专家评审
```

---

### 场景2：评审不通过

**处理**:
1. 分析专家反馈
2. 更新TODO（记录问题和修复方案）
3. 按优先级修复
4. 重新测试
5. 重新提交评审

**禁止**:
- ❌ 跳过评审直接提交
- ❌ 部分修复后提交

---

### 场景3：跨阶段依赖

**处理**:
1. 在TODO中明确标注依赖关系
2. 优先完成依赖项
3. 依赖项评审通过后继续

**示例**:
```markdown
## 阶段5A：组合风险分析器 ⚠️ 待评审
**依赖**: 阶段4（国际化配置层）完成
**状态**: 等待依赖项评审通过
```

## 📊 质量标准

### 代码质量

- ✅ 测试覆盖率 ≥ 90%
- ✅ 所有测试必须通过
- ✅ 类型注解覆盖率 ≥ 95%
- ✅ 代码重复率 < 5%
- ✅ 方法复杂度 Cyclomatic ≤ 10

---

### 文档质量

- ✅ 每个模块有独立TODO.md
- ✅ TODO按优先级分类
- ✅ 专家建议必须记录
- ✅ 代码注释完整（包含TODO注释）
- ✅ 架构文档与代码同步

---

### 评审标准

**通过条件**:
- ✅ 功能实现正确
- ✅ 测试全部通过
- ✅ 代码质量达标
- ✅ 文档完整
- ✅ 符合架构设计

**阻塞条件**:
- ❌ P0问题未修复
- ❌ 测试失败
- ❌ 架构违反
- ❌ 安全问题

---

## 🚨 常见错误与避免

### 错误1：未经测试提交

**表现**: 修改代码后直接提交，未运行测试

**后果**: 破坏现有功能，导致CI失败

**避免**:
- ✅ 每次修改后立即运行测试
- ✅ 使用pre-commit hook自动测试

---

### 错误2：提前追加ask.md

**表现**: 生成ask.md后立即追加到consultation.md

**后果**: 用户未确认就记录，可能需要修改

**避免**:
- ✅ 生成ask.md后等待用户确认
- ✅ 确认后才追加到consultation.md

---

### 错误3：忘记清空consultation.md

**表现**: 阶段提交后不清空consultation.md

**后果**: 旧内容混入新阶段，混乱

**避免**:
- ✅ 每个阶段提交后立即清空
- ✅ 只保留标题 `# 专家咨询记录`

---

### 错误4：专家建议未记录TODO

**表现**: 提取专家建议后直接实施，未记录TODO

**后果**: 改进建议丢失，无法追踪

**避免**:
- ✅ 提取专家建议后立即更新TODO
- ✅ 按优先级分类记录
- ✅ 独立提交TODO更新

---
