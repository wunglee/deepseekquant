## 一、模块概述

### 1.1 模块定位

**数据模块（core/data）**是DeepSeek量化交易系统的数据治理子系统，提供从数据获取、质量验证、质量评估到质量报告的完整能力，为风险、组合、信号等上层模块提供可靠数据基础。

**在系统架构中的位置**:
```
deepseekquant/
├── core/
│   ├── data/            # ← 数据模块（本模块）
│   ├── risk/            # 风险管理模块
│   ├── portfolio/       # 组合管理模块
│   └── execution/       # 执行模块
```

**核心职责**:
1. **数据获取**: 多数据源历史/实时/宏观/基金/股票数据
2. **数据验证**: 完整性、时间一致性、范围合理性、交叉源一致性
3. **数据质量**: 质量指标计算、异常检测、质量监控策略
4. **质量报告**: 质量评估与告警输出
5. **数据模型**: 统一的数据结构与质量描述

### 1.2 业务价值
- **可靠性提升**: 保证数据质量，降低上层模块的错误传播
- **可用性增强**: 统一接口与模型，简化调用与维护成本
- **可观测性**: 提供质量报告与历史统计，支持运营监控与问题定位

## 三、核心业务流程

### 3.1 数据获取主流程
```
上层请求（symbols/period/interval/data_type）
        ↓
┌───────────────────┐
│ DataProcessor     │ ← 路由请求
└───────────────────┘
        ↓
┌───────────────────┐
│ DataFetcher       │ ← 缓存命中/主源获取/备用源重试
└───────────────────┘
        ↓
┌───────────────────┐
│ 缓存写入与统计     │ ← 内存TTL/LRU/Redis（可选）
└───────────────────┘
        ↓
返回 Dict[str, List[MarketData]]
```

### 3.2 数据验证流程
```
输入：List[MarketData]
        ↓
┌───────────────────┐
│ DataValidator     │ ← 价格/成交量/时间/完整性/交叉源验证
└───────────────────┘
        ↓
计算通过率/记录历史 → 返回 {valid, errors, warnings, ...}
```

### 3.3 数据质量报告流程
```
输入：Dataset + DataQualityPolicy
        ↓
┌───────────────────┐
│ DataQualityMonitor│ ← 策略驱动校验（completeness 等）
└───────────────────┘
        ↓
┌───────────────────┐
│ DataQualityReporter│ ← 统计/趋势/建议/告警
└───────────────────┘
        ↓
返回 QualityReport/QualityFlags/告警记录
```

## 四、关键设计决策

### 4.1 分层架构的设计理由
**问题**: 数据获取与质量治理涉及外部依赖与策略逻辑，如何组织代码？

**决策**: 采用四层架构（数据模型层→技术支撑层→业务服务层→业务协调层）

**理由**:
1. **职责分离**: 适配器/缓存与业务逻辑分离，降低耦合
2. **可测试性**: 服务层可通过依赖注入替换实现，便于Mock与隔离测试
3. **可维护性**: 外部依赖变化不影响核心接口；策略变化不影响模型
4. **可扩展性**: 新增数据源/策略仅需扩展Service层

### 4.2 委托模式 vs 继承模式
**问题**: DataProcessor 应继承具体服务，还是委托并支持注入？

**决策**: 采用委托模式（Composition over Inheritance）+ 依赖注入（DI）

**实现**:
```python
# 选择的方案（委托 + DI）
class DataProcessor:
    def __init__(self, config, fetcher: Optional[DataFetcher] = None,
                 validator: Optional[DataValidator] = None,
                 monitor: Optional[DataQualityMonitor] = None):
        self.fetcher = fetcher or DataFetcher(config)
        self.validator = validator or DataValidator(config)
        self.monitor = monitor or DataQualityMonitor(DataQualityPolicy())

    def process(self, data: Dict[str, Any]) -> Dict[str, Any]:
        # 路由到具体服务
        ...

# 拒绝的方案（继承）
# class DataProcessor(DataFetcher):  # 不推荐
#     pass
```

**权衡**:
- ✅ 委托优势: 松耦合、可替换实现、测试友好
- ❌ 继承问题: 强耦合、破坏封装、演进困难

### 4.3 缓存策略设计
**问题**: 历史/实时数据获取存在外部延迟与带宽瓶颈，如何优化？

**决策**: 三级缓存策略（内存TTL/LRU + 可选Redis）

**实现**:
```python
# 1. 内存缓存（TTL/LRU）
cache_ttl[key] = data  # 带过期时间
cache_lru.put(key, data)

# 2. Redis缓存（可选）
redis.setex(f"deepseekquant:{key}", ttl, zlib.compress(pickle.dumps(data)))

# 3. 备用源重试
results = await try_fallback_sources(symbols)
```

**权衡**:
- ✅ 性能提升: 外部调用减少，平均响应时间显著下降
- ❌ 一致性维护: 缓存过期与刷新策略需权衡

### 4.4 适配器模式（数据源）
**问题**: 多数据源（Tushare/AKShare/YFinance等）如何统一？

**决策**: 通过统一适配器接口注入具体实现

**实现**:
```python
class MarketDataAdapter(Protocol):
    async def fetch(self, symbol: str, period: str, interval: str, data_type: str) -> List[MarketData]: ...
```

## 六、性能指标与SLA

### 6.1 性能基准
| 操作 | 规模 | 目标响应时间 | 状态 |
|------|------|-------------|------|
| 历史数据获取 | 100符号/1年 | <3秒（缓存命中） | ✅ 规划 |
| 实时数据获取 | 100符号 | <500ms（单次拉取） | ✅ 规划 |
| 质量报告生成 | 7天窗口 | <2秒 | ✅ 规划 |

### 6.2 可靠性指标
- **可用性**: 99.9%（月度停机时间<43分钟）
- **准确性**: 跨源价格差异≤1%，成交量差异≤5%
- **时效性**: 实时数据延迟<1秒（行情源），历史数据延迟<24小时
