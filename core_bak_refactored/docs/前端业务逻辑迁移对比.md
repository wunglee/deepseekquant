# 前端业务逻辑迁移对比

## 📊 代码行数对比

### 修改前
- **前端业务逻辑**：~120行（周期判断、ISO周计算、OHLCV合并）
- **后端API**：~20行（简单返回实时K线）
- **总计**：~140行

### 修改后
- **前端业务逻辑**：~30行（纯数据覆盖/追加）
- **后端API**：~70行（周期处理、合并调用）
- **总计**：~100行

### 优化效果
- ✅ 总代码量减少 **28%**
- ✅ 前端代码减少 **75%**
- ✅ 前端业务逻辑 **完全移除**

## 🎯 设计原则体现

### 1. 关注点分离（Separation of Concerns）
- ✅ 前端：UI展示、用户交互
- ✅ 后端：业务逻辑、数据处理

### 2. 单一职责原则（Single Responsibility Principle）
- ✅ 前端：只负责将数据渲染到图表
- ✅ 后端：负责数据获取、周期转换、合并计算

### 3. 依赖倒置原则（Dependency Inversion Principle）
- ✅ 前端依赖后端提供的抽象接口（完整的周期K柱）
- ✅ 不依赖具体的合并实现细节

### 4. DRY原则（Don't Repeat Yourself）
- ✅ 周期判断逻辑在后端统一实现
- ✅ 三个周期（日/周/月）复用相同的机制

## 💡 关键设计决策

### 决策1: 前端传递period参数
**原因**：后端需要知道前端当前展示的周期，才能返回对应的K柱数据

**实现**：
```javascript
// 前端
const url = `/api/v1/data/kline/realtime?index_id=${indexId}&period=${currentPeriod}`
```

### 决策2: 后端返回完整的周期K柱
**原因**：前端不应该关心如何合并，只需简单覆盖/追加

**实现**：
```python
# 后端
if period in ['weekly', 'monthly']:
    # 合并逻辑
    merged_price_data = provider.merge_realtime_kline_to_period(...)
    return 最后一个K柱  # 完整的周期K柱
else:
    return 实时K线  # 日线K柱
```

### 决策3: 历史数据排除最后一个周期
**原因**：交易时段将历史和实时分离，避免数据重复

**实现**：
```python
# ChartDataAssembler
if needs_realtime_kline:
    price_data = self._slice_price_data(price_data_full, 0, -1)  # 排除最后一条
```
